## Method

Nothing here is from code inspection alone. A production-shaped dataset was
generated and every claim comes from `EXPLAIN (ANALYZE)`, a timed benchmark, the
Postgres slow-query log, or an HTTP load test.

- **Environment:** 4 vCPU / 16 GB container, PostgreSQL 16 (local, real — not
  embedded), Node 22, one app instance. Load generator on the same host, which
  makes the absolute throughput numbers a floor rather than a ceiling.
- **Dataset:** 20 tenants × 2,000 products, 300,000 orders, **2,100,000 order
  lines**, 282,060 payments, **1,974,420 inventory movements**, 10,000 customers.
  Generated by the new `scripts/perf/seed-scale.sql` in ~2 minutes.
- **Harness (all new, all committed):** `scripts/perf/seed-scale.sql`,
  `explain.ts` (plan + latency budgets, non-zero exit on regression),
  `load-test.ts` (dependency-free HTTP load test, five profiles),
  `profile-checkout.ts` (phase-level event timing).

| # | Finding | Evidence | Status |
|---|---|---|---|
| 1 | Every authenticated query ran in its own transaction — 4 round trips per statement | benchmark: 0.85 ms p50/query; 3,448 q/s @ concurrency 100 | **fixed** → 0.38 ms, 6,579 q/s |
| 2 | POS stock check seq-scanned all 2.1M order lines, once per basket line | `EXPLAIN ANALYZE`: **1,086 ms**, `Rows Removed by Filter: 2,099,936` × 3 loops | **fixed** → 1.1 ms (945×) |

| 4 | N+1 line INSERTs on order create; N+1 product SELECTs on cart update | code + round-trip count | **fixed** → single statements |
| 5 | Inventory applied per line, each its own transaction, locks taken in basket order | profiler | **fixed** → one transaction, ordered locking (also removes a deadlock hazard) |
| 6 | No `statement_timeout` outside explicit transactions | new test fails without the fix (`pg_sleep(3)` succeeded) | **fixed** → pool startup options |
| 7 | Rate-limit tiers were dead code — every tenant limited as `standard` (10 req/s) | `tenantRateLimitMiddleware` mounted with no `tierOf` | **fixed** → resolved from subscription plan |
| 8 | `/readyz` 503'd on `waiting > 0` — i.e. on normal load | measured 33–37 waiters while inside latency budget | **fixed** → threshold on `PG_READY_MAX_WAITING` |
| 9 | `/readyz` returned **500** when the pool was saturated | reproduced while writing the test for #8 | **fixed** → 503 "database unreachable" |
| 10 | **POS checkout runs a synchronous orchestration workflow in the HTTP request** | profiler: `publish:order.created` = **90%** of request time | **OPEN — the blocker** |

### On finding #10, and why it took so long to name

It was chased through every plausible cause first, and each was eliminated by
measurement rather than by argument:

- Slow SQL — `log_min_duration_statement=150` logged **zero** statements from the
  checkout path under load.
- WAL fsync — `synchronous_commit=off` moved p50 1,148 → 936 ms. Not dominant.
- Connection pool — sizes 10 / 25 / 50 under identical load gave 1,218 / 1,104 /
  1,070 ms. Within noise.
- CPU — sampled at under 50% of one core during a blended run, which is what
  made it look like a non-cause. A later dedicated probe under single-scenario
  load showed the process actually pegs a core at 100–110%; see the correction
  below. The early sample was too coarse, not wrong about the checkout.

Timing the event fan-out found it immediately: `EventBus._dispatch` awaits
subscribers sequentially, and `order.created` runs a workflow-engine cycle
(`workflow.started` → 4× `step_completed` → `completed`), an accounting posting
and the inventory application, all inline. In-process (no HTTP, no load
generator) checkout throughput plateaus at ~111/s while average latency grows
72 → 292 ms from concurrency 8 to 32.

**One correction, recorded rather than quietly fixed.** A first draft of the
report attributed the whole ~120 req/s per-instance throughput ceiling to this
handler chain. A read-only load run disproved it — reads alone reach the same
~124 req/s — and a CPU probe found the cause: the Node process saturates **one
core** (100–110%) while Postgres sits at ~10%. So the throughput ceiling is
single-process CPU (a scaling decision, §6), and finding #10 is a latency and
CPU-cost defect on top of it. Both matter; conflating them would have pointed the
next session at the wrong fix.

The elimination table is in `SCALABILITY.md` because the negative results are
worth as much as the positive one to whoever picks this up next.

## Not run — stated, not softened

- **Web gates** (`web` typecheck / lint / vitest / build) — no `web/**` file was
  changed by this work, and the container's time was spent on measurement.
- **Playwright e2e** — no built-and-served real-stack pair here; CI runs it.
- **`extreme` load profile (800 in-flight, ~20,000 active users)** — deliberately
  skipped. Against a single instance whose core is already saturated at ~120
  req/s it would have measured queue depth, not capacity. Run it against a
  multi-instance deployment after finding #10 is fixed.
- **Failure-injection** — Postgres/Redis/payment-provider outages, worker crashes,
  concurrent-oversell races. Not exercised.
- **Frontend performance** — no bundle analysis or page-level measurement.
- **Security** — MFA, sessions/refresh tokens, CSRF, uploads, webhook signature
  verification, dependency CVEs were **not** re-verified. The rate-limiting and
  tenant-isolation findings above are the only security-adjacent items covered.
- **First load-test sweep discarded.** An initial sweep ran while the full
  backend suite was executing on the same 4 vCPUs. Those numbers were thrown away
  and every figure reported comes from a re-run on an idle host.
