## 0. Executive summary

Ascend's **code** is materially stronger than its **operations**. That gap is
the finding; nearly everything else is detail.

The application is a genuinely well-built modular monolith: 55 modules, 186
tables, 261 indexes, 98 backend test files, integer-cents money, tenant scoping
with an RLS backstop, a transactional outbox with durable redelivery, race-free
document numbering, immutable inventory movements, and an append-only ledger.
Design decisions are recorded in ADRs, duplication is actively policed by
purpose-built scanners, and the repo's own audit trail is unusually honest about
what is and is not built.

Against that, the operational floor has holes an enterprise buyer will find in
the first hour of diligence:

1. **No production backup has ever run.** `backup.yml` has reported success 16
   times while skipping every real step, because `PROD_DATABASE_URL` is unset
   and the workflow skips cleanly rather than failing. The honest RPO is not
   ≤24h — it is total loss. There are also no down-migrations in the repo, so
   there is no rollback path for a bad data migration either.
2. **Nobody knows where production is.** Three of this repo's own documents
   assert Render; zero lines of deploy automation support it; the claimed URL
   times out from three independent networks. The heartbeat has been red for
   ~30 consecutive runs against a hostname that returns `DEPLOYMENT_NOT_FOUND`.
3. **Two CI security guards had never evaluated the codebase.** One was fixed
   2026-08-05. The other — unguarded mutation routes — was still inert when this
   audit started, and reproducing it locally produced 39 matching lines *and* a
   green ✓ *and* exit 0 in the same run. Fixed in this change; see §12.
4. **No secret scanning, no SBOM, no licence inventory, no SAST, no container
   scanning** existed. Three of the four are now in place (§12); SAST and
   container scanning are recommended and not implemented, for reasons given.
5. **Observability is instrumented but unwatched.** Prometheus metrics, W3C
   trace IDs, structured JSON logs and a Sentry envelope all exist in code.
   Nothing scrapes the metrics, no backend receives the traces, and there is no
   alerting beyond a GitHub Actions heartbeat that emails on a red run.

**Overall production readiness: 61 / 100** (§11). Architecture and
maintainability score in the 80s; observability, deployment and compliance in
the 30s and 40s. The score is dragged down almost entirely by things that are
one configured secret or one confirmed dashboard fact away from being fine —
which is the optimistic reading, and also why they have stayed open so long.

**The single highest-value action is not in this repo.** It is setting
`PROD_DATABASE_URL` so a backup runs. Everything else can wait a week; that one
cannot, because until it is done, every day of production operation is a day of
unrecoverable data.

### 1.3 Per-service assessment

Abbreviated to the decision each one actually needs. Full alternatives
comparison in Phase 2.

**Supabase (Postgres).** *Why:* managed Postgres with a free tier, no ops.
*Used by:* the backend only — never the frontend, and none of Supabase's other
products. *Advantages:* zero DBA overhead, PITR on paid tiers, good pooler.
*Disadvantages:* the shared pooler's per-project client limit is shared across
every process *and* every tool (psql, seeds, `db:check`), which is why
`.env.example` recommends `PG_POOL_MAX=5` on small plans. Session mode (5432) is
mandatory here because `openDb()` pins `search_path` via a startup parameter that
transaction mode does not carry — a real constraint that rules out the cheaper
pooling mode. *Lock-in:* **low** — it is plain Postgres, and nothing uses
Supabase-specific APIs. This is the single best lock-in position in the stack and
worth protecting. *Verdict:* **keep.**

**Vercel (frontend).** *Why:* zero-config Next.js hosting. *Advantages:*
best-in-class Next.js support, previews per deploy. *Disadvantages:* the backend
deploy path through Vercel is confirmed broken and half-configured alongside a
claimed Render backend. *Lock-in:* **low** for the frontend (Next.js standalone
output runs anywhere; the `Dockerfile` and `docker-compose.yml` already prove
it). *Verdict:* **keep for frontend; delete the backend deploy path** once §7's
hosting question is answered.

**Render (backend, claimed).** *Verdict:* **confirm or abandon — do not leave
both paths half-configured.** This is `DEPLOYMENTS.md`'s P1 and it is the
blocker for six other findings in this audit.

**Redis.** *Why:* distributed rate limiting and cross-instance event fan-out.
Optional by deliberate doctrine. *Risk:* the fallback is silent. On a
multi-instance deploy without `REDIS_URL`, every replica keeps **separate**
rate-limit buckets, so the effective limit is N× the configured one — the app
warns at boot in production, and a boot warning is not an alert. *Verdict:*
**keep optional; make it required the moment there is more than one instance,
and assert it rather than warn.**

**Stripe.** *Why:* card payments plus Terminal hardware. *Advantages:* keeps
card data entirely out of Ascend's database, which is what holds PCI scope at
SAQ-A. Circuit-breaker wrapped (`src/modules/payments/stripe.ts`). *Lock-in:*
**high** — Terminal especially is hardware-coupled. *Verdict:* **keep.** The
lock-in is worth it; the PCI scope reduction alone justifies it.

**SendGrid.** *Why:* transactional email. *Implementation:* raw `fetch`, no SDK
— genuinely elegant, no dependency. *Disadvantages:* deliverability tooling is
weaker than Resend/SES, and `EMAIL_WEBHOOK_URL`'s purpose is inferred from its
name, never traced to a call site. *Lock-in:* **near zero** — one function,
`src/shared/email.ts`. *Verdict:* **replaceable at will; no urgency.**

**Sentry.** *Why:* error tracking. *Implementation:* a hand-rolled envelope POST,
no SDK. *Disadvantages:* this is the weakest link in the observability chain.
It captures message, a 5-frame stack of raw strings, and three tags. It has **no
release tracking, no source maps, no breadcrumbs, no user context, no
performance data, and no frontend coverage at all** (`web/app/error.tsx` says
"when wired in production" — it is not wired). *Verdict:* **adopt the real SDK
or replace.** See Phase 2.

**Anthropic.** *Why:* narrate deterministic signals (ADR-005). Circuit-breaker
wrapped, explain-only, human approval for writes. *Verdict:* **keep, and keep
the constraint** — it is the right posture for an ERP.

## Phase 2 — Alternatives compared

Scored for *this* system: a modular monolith with one Postgres, a small team, a
retail-first ERP, and an operations backlog that is the actual bottleneck. A
technically superior option that costs a month of migration loses to a good
option that costs a day, because the month is better spent on Phase 3 and 4.

### 2.1 Database

| Option | Cost (small prod) | Enterprise | Scale | Migration | Notes |
|---|---|---|---|---|---|
| **Supabase (current)** | $25/mo Pro | Good — PITR, SOC 2 | Vertical + read replicas | — | Session-mode pooling constraint (§1.3) |
| Neon | ~$19/mo | Good | Autoscale, scale-to-zero, branching | Low (plain PG) | DB-per-PR branching would suit this repo's parallel-agent workflow well |
| AWS Aurora PostgreSQL | ~$200+/mo | Excellent | Very high | Medium | Real answer at 10k+ tenants; overkill now |
| Google AlloyDB | ~$300+/mo | Excellent | Very high, strong analytics | Medium | Same |
| CockroachDB | ~$300+/mo | Excellent | Horizontal, multi-region | **High** | No true `SERIAL`/advisory-lock parity; would break the migration lock and `FOR UPDATE` patterns this codebase depends on |
| PlanetScale | ~$39/mo | Good | Horizontal | **Very high** | MySQL. Would require rewriting every one of 186 tables and all raw SQL. **Rejected outright** |

**Recommendation: stay on Supabase.** Revisit at either (a) sustained >70% CPU
on the largest reasonable instance, or (b) a compliance requirement for a region
Supabase does not serve. Neon is the standby if branching-per-PR becomes
valuable enough to justify a migration that is otherwise unnecessary.

### 2.2 Backend hosting

| Option | Cost | Enterprise | Scale | Migration | Notes |
|---|---|---|---|---|---|
| **Render (claimed)** | $7–25/mo | Good | Vertical + horizontal | — | Persistent process, no cold starts, native cron, Docker-native. Fits this app well — **if it is actually running** |
| Fly.io | ~$5–30/mo | Good | Multi-region, edge | Low | Best latency story for multi-region retail; more ops than Render |
| Railway | ~$5–20/mo | Fair | Vertical | Low | Simplest; weakest compliance posture |
| AWS App Runner | ~$25–50/mo | Excellent | Auto | Medium | Best enterprise-credibility-per-effort on AWS |
| AWS ECS Fargate | ~$30–70/mo | Excellent | High | Medium-high | Needs real IaC |
| Google Cloud Run | ~$10–40/mo | Excellent | Scale-to-zero | Low | Container-native, generous free tier; cold starts return |
| Kubernetes | $70+/mo + ops | Excellent | Very high | **Very high** | **Standing rejection in `ARCHITECTURE.md`. Do not re-litigate.** Correct for a 55-module monolith with one datastore |
| Vercel serverless (current CI path) | Usage | Fair | Auto | — | **Wrong for this app.** Cold starts on every migration-running boot, no persistent process for the outbox sweep, `setInterval` pollers freeze between invocations — which is *why* `/jobs/tick` exists at all |

**Recommendation: Render, confirmed and wired.** The app is already
container-ready (`Dockerfile`, non-root, now with a `HEALTHCHECK`) and
`src/server.ts` binds `process.env.PORT` with no host restriction, so it is
correct for Render today. The work is not technical — it is confirming the
dashboard facts in `DEPLOYMENTS.md` P1 and then deleting whichever of the two
half-configured paths loses. **Cloud Run is the strongest alternative** if a
GCP-shaped enterprise buyer ever appears.

### 2.3 Frontend hosting

Vercel (current) vs Netlify vs Cloudflare Pages. **Recommendation: stay.** Next.js
14 App Router support on Vercel is materially ahead of both alternatives, the
frontend half of the deploy pipeline is the half that works, and `output:
"standalone"` keeps the exit door open. Cloudflare Pages would cut cost at high
bandwidth; there is no bandwidth problem to solve.

### 2.4 Object storage — **the gap, not the choice**

There is no object storage at all. Not "the wrong one" — none. This is the root
cause of the EDI-import gap (§9): the frontend "upload" form never sends file
bytes because there is nowhere to put them.

| Option | Cost | Notes |
|---|---|---|
| **Cloudflare R2** | $0.015/GB, **$0 egress** | Zero egress is decisive for product images and receipt PDFs served repeatedly |
| AWS S3 | $0.023/GB + egress | Deepest ecosystem, most expensive to serve from |
| Supabase Storage | Bundled | Already have the vendor; couples storage to the one dependency with currently-low lock-in |
| Backblaze B2 | $0.006/GB | Cheapest; smallest ecosystem |

**Recommendation: Cloudflare R2**, S3-compatible API, behind a thin
`src/shared/storage.ts` seam so the provider stays swappable. Explicitly **do not
use Supabase Storage** — Supabase is currently the lowest-lock-in dependency in
the stack precisely because only plain Postgres is used, and that is worth more
than the convenience.

### 2.5 Authentication

Ascend has built its own: JWT sessions, refresh rotation, API keys with scopes,
TOTP MFA with backup codes, account lockout, per-tenant OIDC SSO, custom roles.
That is a genuinely large amount of working, tested code.

| Option | Cost at 50 users | Migration | Verdict |
|---|---|---|---|
| **Current (self-built)** | $0 | — | **Keep** |
| Clerk | ~$25/mo + $0.02/MAU | High | Better UX, worse fit for per-tenant IdP config |
| Auth0 | ~$35/mo, steep curve | High | Enterprise SSO is its strength; expensive |
| Keycloak | Self-host + ops | High | Full control, real ops burden |

**Recommendation: keep.** Migrating auth is the highest-risk refactor available
and would buy nothing this system lacks. The two real gaps are narrow and worth
fixing in place: **OIDC PKCE + nonce** (listed as an open IdP-compatibility
decision in `LOOP_STATE.md`) and per-tenant IdP secrets living in `settings_kv`
rather than a secrets manager (§4).

### 2.6 Caching · Queues · Search

- **Caching:** Redis (current, optional) vs **Upstash Redis** (per-request
  pricing, HTTP API, serverless-friendly) vs Valkey (OSS fork). *Recommendation:*
  **Upstash** the moment the backend runs more than one instance — it removes the
  "did anyone remember to set `REDIS_URL`" failure mode at near-zero idle cost.
- **Queues:** the current `job_queue` table with `FOR UPDATE SKIP LOCKED` plus a
  transactional outbox is the *right* pattern for a monolith with one Postgres.
  BullMQ adds a Redis dependency for less transactional safety; **Kafka and
  RabbitMQ are standing rejections** and correctly so. *Recommendation:* **keep.**
  Fix the daily tick cadence (§6), not the architecture.
- **Search:** `ILIKE` + `pg_trgm` GIN. *Recommendation:* **keep.** Meilisearch or
  Typesense only on a measured bottleneck — which `ARCHITECTURE.md` already says,
  and which remains right. Elasticsearch/OpenSearch are disproportionate.

### 2.7 Observability — where the real decision is

Current state: Prometheus metrics rendered but never scraped; W3C trace IDs
generated but exported nowhere; structured JSON logs to stdout with no
aggregator; a hand-rolled Sentry envelope with none of Sentry's actual value; and
a GitHub Actions heartbeat as the only alerting.

| Option | Cost (small) | Covers | Migration |
|---|---|---|---|
| **Better Stack** | ~$25/mo | Logs + uptime + on-call + status page in one | **Low** |
| Grafana Cloud | Free tier → ~$50/mo | Metrics + logs + traces (Prometheus/Loki/Tempo) | Low — `/metrics` is already Prometheus-format |
| Sentry (real SDK) | ~$26/mo | Errors + performance + release tracking, front and back | Low |
| Datadog | ~$15/host/mo + per-signal | Everything | Medium — costs escalate fast |
| New Relic | Free 100GB/mo | Everything | Medium |
| Self-hosted Prom+Grafana+Loki | Infra + ops | Everything | High |

**Recommendation, in order:**
1. **Sentry's real SDK**, backend and frontend. Highest value per hour of work;
   `web/app/error.tsx` is already waiting for it. Replaces §1.3's weakest link.
2. **Grafana Cloud** free tier scraping the existing `/metrics`. The endpoint,
   the token auth and the metric names already exist — this is configuration,
   not engineering.
3. **Better Stack** for uptime + on-call + a public status page, replacing the
   heartbeat as the alerting path (it also fixes "alerts go to whoever watches
   the repo").
4. **OpenTelemetry** only when there is a second service to trace *between*.
   Today it would add a dependency to correlate a monolith with itself.

Each row is code-verified. "Instrumented but unwatched" is used precisely: the
signal is produced and nothing consumes it — which is worse than absent, because
it reads as covered.

| Capability | Status | Evidence |
|---|---|---|
| Application monitoring | 🔶 Instrumented, unwatched | `/metrics` renders Prometheus text; nothing scrapes it |
| Infrastructure monitoring | ❌ Missing | No host/container metrics anywhere |
| Database monitoring | 🔶 Partial | `/readyz` returns live pool stats and 503s on exhaustion — genuinely good. No query-level metrics |
| Redis monitoring | ❌ Missing | Connection errors log; nothing tracks them |
| API monitoring | 🔶 Instrumented, unwatched | `http_requests_total` + duration summary, path-normalised |
| Endpoint health | ✅ Built | `/healthz` (liveness), `/readyz` (readiness + DB + pool), `/health` (module list) |

| Heartbeat checks | 🔶 Same workflow | Same |
| Business metrics | 🔶 Partial | UOM conversion and POS barcode counters exist (`metrics.ts`) — narrow but real |
| Performance metrics | 🔶 Instrumented, unwatched | Duration summary only; **no percentiles** — a summary of sum/count cannot produce p95 |
| User analytics | ❌ Missing | None |
| Error tracking | 🔶 Weak | Hand-rolled Sentry envelope, backend only. No releases, source maps, breadcrumbs or user context |

| Alerting | 🔶 Floor only | A red Actions run emails repo watchers. No channel, no severity, no routing, no on-call |
| Incident management | ❌ Missing | No runbooks, no on-call, no escalation |
| Status page | ❌ Missing | None |

### Recommendations, ordered

1. **Point the heartbeat at a real URL.** Blocked on `DEPLOYMENTS.md` P1, not on
   engineering. Until then the monitor is noise, and a monitor everyone has
   learned to ignore is worse than none. *(This change makes `smoke-test` read
   the same variable so it cannot drift again — §12, ADR-009.)*
2. **Sentry SDK, both halves.** ~2 hours. Largest single jump in this table.
3. **Scrape `/metrics`** with Grafana Cloud's free tier. The endpoint and token
   auth already exist.
4. **Replace the duration summary with histogram buckets.** p95 is the number
   anyone will actually ask for, and the current shape cannot produce it.
5. **Add memory/CPU/event-loop-lag gauges** to `/metrics` — a few lines against
   `process.memoryUsage()` and `perf_hooks.monitorEventLoopDelay()`.
6. **Export queue depth and outbox-pending as metrics.** Outbox-pending is the
   single best early-warning signal this system has: it rises before anything
   user-visible breaks.
7. **Real alerting** (Better Stack or Grafana OnCall) with a status page.
8. **Domain KPI metrics** — sales/hour, failed payments, stockouts, receiving
   throughput. These are what a retail operator pages on, and none exist.

## Phase 4 — Security audit

### 4.1 Strong

Verified by reading the implementations, not the docs.

| Control | Assessment |
|---|---|
| Authentication | **Strong.** JWT with explicit `algorithms: ["HS256"]` — pinned, so the `alg: none` and RS/HS confusion attacks are closed. Required-claims check. API keys with scopes |
| MFA | **Strong.** TOTP + backup codes, tested |
| SQL injection | **Strong.** `@name` → `$n` compilation, values always bound. All 6 interpolation sites reviewed 2026-08-05 and confirmed identifier-only. CI guard now genuinely enforces this |
| Tenant isolation | **Strong — the best control in the system.** SQL filtering, an `AsyncLocalStorage` tenant context, `set_config('app.tenant_id', …, true)` on every transaction, and Postgres RLS with `FORCE ROW LEVEL SECURITY` underneath. A forgotten `WHERE tenant_id` cannot leak rows. Independently swept and verified clean (iteration 9) |

### 4.2 Findings

**F-1 — CI's unguarded-mutation-route guard could not fail. `CRITICAL` (process). FIXED in this change.**
The step ended `! grep … || echo "…✓"`. Reproduced locally: 39 matching lines,
the ✓, and exit 0, in the same run. It had **never once evaluated this
codebase**. Worse, its detection was wrong in both directions — it excluded a
line only if the literal `requireRole` appeared on it, but 44 route files declare
`const mgr = requireRole("manager")` and pass `mgr`, and `-A1` meant middleware
on a later line read as guarded. Replaced with `tools/route-guard-scan.mjs` (§12).

**F-2 — 76 mutating routes carry no authorization middleware. `HIGH` (subset). DOCUMENTED, not fixed.**
Found by the new scanner: 314 mutating routes across 49 files, 76 unguarded. Most
are correct — POS and floor operations *should* be open to cashiers. Each of the
76 is now individually classified in `tools/route-guard-allowlist.json` as
`open-by-design:`, `in-handler:`, or `GAP:`. **The `GAP:` set is real
authorization debt:**

| Route | Why it matters |
|---|---|
| `catalog POST /` | A cashier can create products. Every sibling bulk path is `requireRole("manager")` |
| `catalog POST /:id/barcodes` | A cashier can attach a barcode — and therefore a pack-size/UOM conversion (ADR-006) — to a product |
| `catalog PUT /:id/categories` | A cashier can re-categorise, moving a product in reporting and package gating |
| `billing POST /bills` | A cashier can create an AP bill. `POST /bills/:id/pay` **is** guarded — the money step is covered, the document is not |
| `billing POST /invoices` | A cashier can raise an AR invoice against a customer |
| `quotes PATCH /:id/status` | A cashier can accept/reject/expire any quote. The module imports no guard at all |
| `quotes POST /:id/convert` | Converting creates a real order at quoted prices |
| `quotes DELETE /:id` | Destructive and ungated |
| `customers DELETE /:id/addresses/:addressId` | Destructive and ungated |
| `customers PATCH /:id/addresses/:addressId` | Ungated, unlike the contact routes beside it |
| `outlets POST /` | Creating an outlet is setup, not till work |
| `outlets POST /:outletId/registers` | Registering a till is setup, not till work |
| `inventory POST /pipeline/reorder-alerts/:id/create-po` | Creates a real PO while purchasing's own PO routes are mgr-guarded |
| `inventory POST /pipeline/receiving/:id/update` | Mutates receiving progress ungated |

Deliberately **not** fixed here. Re-roling 14 routes changes who can do what in a
live POS, needs product judgement about floor workflows, and belongs in its own
reviewable PR — not inside an infrastructure audit. The allowlist makes the debt
un-loseable and the scanner stops it growing, which is the durable half.

*Related smell:* `catalog POST /import` and `/import-csv` **do** check
owner/manager in-handler, but throw `badRequest` (**400**) where the rest of the
codebase returns **403**. Clients cannot distinguish "malformed" from
"forbidden".

**F-3 — `JOBS_TICK_SECRET` was documented but never read. `HIGH`. FIXED in this change.**
See §1.2, §12, ADR-010. Silent total loss of background job execution for anyone
following the documentation on a non-Vercel host.

**F-4 — No secret scanning existed. `HIGH`. FIXED in this change.**
`AGENTS.md`'s first hard rule is "never write secrets into any file" and nothing
checked it. First full scan: 4 hits, **all false positives** (two cache-key
constants, a docs example JWT, an audit-doc phrase) — a genuinely clean result,
now recorded in `.gitleaks.toml`. Because the backlog is zero, the check ships
**gating**, verified against planted AWS/Stripe/GitHub credentials.

**F-5 — Timing-unsafe comparison on infrastructure secrets. `MEDIUM`. FIXED in this change.**
`/metrics` and `/jobs/tick` compared with `!==`, leaking shared-prefix length
through response timing. Both endpoints are reachable without a session, so the
secret is the only control. Now `secretsMatch()` — SHA-256 then `timingSafeEqual`.

**F-6 — No SAST. `MEDIUM`. NOT fixed — recommended.**
No CodeQL or equivalent. CodeQL on a private repository requires GitHub Advanced
Security, which is a licensing decision and therefore Sri's. Semgrep is the
no-GHAS alternative. Either must be proven green on a branch before gating
(ADR-008).

**F-7 — No container image scanning. `MEDIUM`. NOT fixed — recommended.**
CI builds the image and never scans it. Trivy in the `docker-build` job,
report-only first. Not implemented here because the Docker daemon is unavailable
in this session and shipping an unverified scanner into CI is exactly what
ADR-008 prohibits.

**F-8 — 14 dependency advisories in `web` (1 critical, 9 high). `MEDIUM`. Pre-existing, tracked.**
Fixes are major migrations (`next` 14→16, `vitest` 2→4), tracked as F-24/F-25.
Report-only in the new `security.yml` with the promotion condition written down.

**F-9 — No secrets manager. `MEDIUM`.**
Credentials live in GitHub Actions secrets and host env vars. No central
rotation, no access audit, no expiry. **Sharpest edge: per-tenant OIDC client
secrets are stored in the `settings_kv` table** — a deliberate architectural
choice (`ARCHITECTURE.md` confirms it), but it means customer IdP credentials sit
in the application database under whatever encryption that table has. Worth an
explicit decision.

**F-10 — `errorEnvelopeMiddleware` is dead code. `LOW`.**
`app.ts` mounts `errorMiddleware` then `errorEnvelopeMiddleware`. The first
always responds and never calls `next(err)`, so the second **never runs**. The
documented envelope `{error:{code,message,requestId}}` is therefore never
delivered — no error response carries a `requestId`, so a customer reporting an
error has nothing to correlate against the logs. No test asserts it (grep for
`requestId` in `src/**/*.test.ts` returns nothing), which is why it survived.
Not fixed here: adding `requestId` changes every error response shape and
deserves its own PR.

**F-11 — Legacy brand origins hardcoded in the CORS default. `LOW`.**
`src/app.ts`'s default allowlist contains `finder-pos.vercel.app`,
`finder-pos-web.vercel.app`, `finder-pos-frontend.vercel.app`. `AGENTS.md`
prohibits hardcoding the old product name. These are dead domains — but a dead
domain in a CORS allowlist is a subdomain-takeover target if the name is ever
re-registered. Setting `ALLOWED_ORIGINS` overrides the default entirely.

**F-12 — `compile()` binds NULL for unmatched named parameters. `MEDIUM` (latent).**
`src/shared/db.ts`'s `@name` compiler silently binds `undefined` → NULL when a
placeholder has no matching key. This has already caused a **total module
outage**: `customer_invoices.create()` used `@subtotal` against a params object
with `subtotal_cents`, so every invoice creation with lines 500'd on a NOT NULL
violation (iteration 19). The class of bug is invisible until a specific write
path is exercised. Fixing it means throwing on a missing key — correct, and
capable of turning a latent NULL into a runtime throw somewhere untested. It
needs its own PR with the full suite as the gate, not a drive-by in an audit.

## Phase 10 — AI and automation

Current posture, and it is the right one: `ai_assistant` narrates deterministic
rule-based signals via Anthropic, explain-only, circuit-breaker wrapped, human
approval for any write (ADR-005). `AGENTS.md` is explicit — AI must not be the
source of truth and must not invent business facts. **Every recommendation below
inherits that constraint.**

**Build on existing deterministic foundations (highest confidence):**
1. **Demand forecasting** — `demand_planning` and `sales-velocity.ts` already
   compute the inputs. Add seasonality and trend; keep the output a *number the
   system computed*, with AI explaining it.
2. **Inventory optimisation** — safety stock, MOQ and pack-size rounding already
   ship. Extend to multi-location rebalancing.
3. **Purchase recommendations** — `insights.createReorderPOs()` exists.
4. **Supplier analysis** — on-time rate and price variance are derivable from
   existing PO data today.

**Needs object storage first (§2.4):**
5. **Invoice OCR** (AWS Textract or Google Document AI) → auto-populate AP bills.
   Highest labour-saving of anything in this list.
6. **Receipt OCR** for expense capture.
7. **Document search** over uploaded POs, invoices and contracts.

**Needs deliberate guardrails:**
8. **Price optimisation** — elasticity from `product_price_history` (already
   append-only). Must stay a *suggestion*; never auto-apply.
9. **Fraud detection** — refund and void patterns per cashier. Anomaly flags for
   human review, never automated blocking.
10. **Natural-language reporting** — text-to-SQL over a **read-only, tenant-scoped
    connection**, never the app's write pool.
11. **AI agents for workflow automation** — explicitly gated on E4 in
    `ARCHITECTURE.md`. Do not start early.

**Note on the existing forecasting stack:** `GAPS.md` already records that
reorder *effectiveness* cannot currently be measured, because a manually-created
PO carries no reference to the reorder alert that prompted it. Any forecasting
work should fix that instrumentation first — otherwise there is no way to tell
whether a model is better than the rule it replaced.

### 12.2 Service dependency graph — failure modes

What actually happens when each dependency dies. This is the table an on-call
engineer needs and the repo did not have.

| Dependency | Criticality | Failure behaviour |
|---|---|---|
| PostgreSQL | **Fatal** | Total outage. `/readyz` fails; app refuses to boot without `DATABASE_URL` |
| Redis | Degraded | Silent fallback to per-instance state. **On multi-instance, rate limits become N× the configured value** |
| Stripe | Degraded | Circuit breaker opens; card tender returns 503. Cash/other tenders keep working |
| SendGrid | Degraded | Email silently fails (logs only). Password reset becomes unusable |
| Anthropic | Degraded | Circuit breaker opens; `ai_assistant` narration unavailable. **No business function lost — by design (ADR-005)** |
| Sentry | Silent | Fire-and-forget; failures swallowed |
| Vercel | Fatal (frontend) | UI unreachable; API unaffected if backend is elsewhere |
| GitHub Actions | Non-runtime | Blocks deploys, backup, heartbeat |

### 12.4 Cost optimisation
